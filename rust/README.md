# frankbot.org -- Cloudflare Pages build

The site is generated by the Rust generator in `rust/`. The Cloudflare
Pages project builds it directly; there is no Next.js build and no
`node_modules` in the build.

## How the build works

`rust/build-pages.sh` runs four steps:

1. **Install Rust.** The Pages v3 build image (Ubuntu 22.04) ships
   Node, Python, Go, Ruby and Bun, but **not Rust**. The script
   installs the toolchain with rustup. The channel comes from
   `rust/rust-toolchain.toml`.
2. **Build the stylesheet.** The Tailwind CLI is fetched with `npx`
   (pinned to the version the Next.js project used), so no
   `package.json` install is needed.
3. **Compile the generator.** `cargo build --release --locked`.
4. **Generate the site.** The generator writes every page, then the
   script copies the static runtime and the vendored font assets on
   top of it.

Output: `out-rs/`.

## Why the fonts are vendored

`globals.css` starts with

```css
@import url("https://fonts.googleapis.com/css2?family=Inter:...");
```

so Google Fonts is the primary source and the browser fetches the
woff2 files from `fonts.gstatic.com`. The three `next/font` CSS
files and the 232 woff2 subsets in `rust/assets/` are the
**fallback** for readers who cannot reach Google -- which includes
readers on networks where it is blocked. Verified in a browser: with
Google Fonts reachable, zero local woff2 are fetched; with it
blocked, the local files load and `Inter` / `Noto Sans JP` render
correctly.

Those assets are produced by `next/font`, which names them by
content hash. They are copied verbatim (byte-identical to the
Next.js build output) so the `@font-face` URLs keep working.

**They are not regenerated.** If the font set changes, the Next.js
build has to run once and the files re-copied into
`rust/assets/_next/static/`.

## Pages project settings

The `openclaw-blog-new` Pages project is Git-connected to this
repository. To switch it to the Rust build, change these settings in
the dashboard under **Settings > Builds & deployments**:

| Setting | Value |
|---|---|
| Framework preset | None |
| Build command | `./rust/build-pages.sh "$PWD" "$PWD/out"` |
| Build output directory | `out` |
| Root directory | `/` (repository root) |
| Node.js version | `22` |

`NODE_VERSION=22` can also be set as an environment variable.

### The output directory has to be `out`

**A `wrangler.toml` at the repository root overrides the dashboard's
output directory.** The build log says so verbatim:

```
Found wrangler.toml file. Reading build configuration...
pages_build_output_dir: out
```

Pages then validates *that* directory, and fails with
`Error: Output directory "out" not found.` when it is missing. The
repository root has a `wrangler.toml` with `pages_build_output_dir =
"out"`, so the dashboard's value is ignored and the build has to
write to `out`.

That is also why the build command passes the directory explicitly:
the local default is `out-rs`, so the Next.js baseline in `out/`
survives for the parity comparison, while the Pages build writes to
`out`.

### The automatic npm install cannot be skipped

Pages runs `npm clean-install` automatically whenever the repository
has a `package.json`, and this repository does -- it is the Next.js
project. That pulls the whole dependency tree (about 670 MB) into a
build that does not need it.

`SKIP_DEPENDENCY_INSTALL=1` does **not** help. The dashboard
environment variables are ignored while a root `wrangler.toml` is
present, and the build log confirms it:
`Build environment variables: (none found)`.

The Rust build installs the one npm package it needs (the Tailwind
CLI) into a scratch prefix of its own, so nothing from `package.json`
is required -- the install is simply wasted work.

If the dependency tree has to go, the repository needs a `package.json`
that Pages does not recognise, or the Next.js project has to move out
of the repository root. That is a bigger change than it looks, and it
is not required for the Rust build to work.

### The build image has a C compiler

The Pages v3 build image (Ubuntu 22.04) **does** ship `cc`, `gcc`,
`ld`, `make` and `ar`, in `/usr/bin`. The build log shows them:

```
Detected the following tools from environment: cc, gcc, ld, make, ar
```

So the system linker is used, which is the normal path.

**Do not shim `cc` to `rust-lld`.** rust-lld is not a gcc driver: it
rejects `-Wl,...` and `-nodefaultlibs`, so the host build scripts fail
to link. The musl-hosted toolchain is only a fallback for an image
without a C compiler, and it is not reachable on the real image.

Run `rust/build-linux-container.sh --no-cc` to exercise that fallback
in a container without a C compiler.

### The line endings have to be LF everywhere

styled-jsx hashes the **text** of a `<style jsx>` block to build its
scope class name (`jsx-<hash>`). CRLF and LF therefore produce
different hashes, so the same source file yields a different class
name on Windows and on Linux.

`src/components/layout/Footer.tsx` was checked out with CRLF (the
repository has `core.autocrlf=true`), so the footer got a different
scope id on Windows:

```
Windows  jsx-e24d6c53b6876061
Linux    jsx-a2842b1a1a80f4d8   <- what production serves
```

The `.gitattributes` at the repository root fixes this:

```
* text=auto eol=lf
```

Every platform now checks the files out with LF, and the build output
is identical everywhere. If a scope id ever differs again, check the
line endings of the component before looking anywhere else.

Two head elements also differ between the platforms, because next/font
behaves differently: the three font preload links and the
`next-size-adjust` meta tag. The Linux build emits both, so the
generator emits both.

### Cutover

The current production build is `npm run build` with the output in
`out/`. Switching the build command is the whole cutover -- there is
no separate deploy step.

**Before switching**, verify the branch build:

```bash
# The exact Pages build, in the same OS the build image uses.
./rust/build-linux-container.sh

# The output must match the Next.js baseline.
python rust/scripts/parity.py out out-rs
```

The branch project `frankbot-rs-branch` already does this on every
push: it is Git-connected to `feat/rust-pages`, runs the same build
command, and its CI compares the result against the Next.js baseline.
Watch <https://frankbot-rs-branch.pages.dev/> before switching.

### The switch

1. Merge `feat/rust-pages` into `master`.
2. On the `openclaw-blog-new` Pages project, set the build command to
   `./rust/build-pages.sh "$PWD" "$PWD/out"`. Leave the output
   directory at `out` -- the root `wrangler.toml` already says `out`,
   so the dashboard value is not what decides it.
3. Push to `master` and wait for the deployment.

The production project is not touched by anything on this branch. The
branch project builds from the same repository, with a different
Pages project, so both can run at the same time.

### Rollback

Set the build command back to `npm run build`. The Next.js
application is still in this repository and still builds, so the
rollback is a one-field change plus a redeploy. Nothing is deleted
during the cutover.

The output directory does not need to change on rollback: it is
`out` for both builds.

### Verify after the switch

```bash
# The deployed site must answer on every route.
for u in / /en.html /ja/blog /zh/about.html /site.js; do
  curl -sS -o /dev/null -w "%{http_code} $u\n" "https://frankbot.org$u"
done

# The build log must not be public.
curl -sS -o /dev/null -w "%{http_code} build-log.txt\n" \
  "https://frankbot.org/build-log.txt"
```

A deployed site is not byte-identical to a local build. The root
`index.html` is really `/ja/` (the `_redirects` redirect), and the
Windows checkout has CRLF where the Linux build has LF. Compare with
the line endings normalised.

## The generator

`rust/` is a standalone Rust crate. It reads the blog content from
the repository root:

- `src/content/posts/` -- the MDX posts
- `messages/` -- the locale strings
- `public/` -- the static files (favicons, `sw.js`, `_redirects`, ...)

`rust/scripts/parity.py` compares two output trees layer by layer
(body skeleton, head, visible text, header/footer bytes).
`rust/scripts/reference.mjs` regenerates the ground-truth corpus
from the live `convertMarkdown()` in
`src/app/[locale]/blog/[slug]/page.tsx`.

The generator writes the same markup as the Next.js build, byte for
byte. The differences that do exist are deliberate:

- `src/site.js` replaces the React runtime. It restores the header
  scroll state, the language switcher, the mobile menu, the blog
  search, the category filter, the terminal line rotation, the avatar
  float and the PWA install prompt.
- The `next/font` CSS and the woff2 subsets are copied rather than
  re-emitted.
- The service worker is not part of the static output.

## The CI baseline build does not use Google Fonts

next/font has no disk cache, so every Next.js build downloads the
fonts from Google again. Google intermittently answers with an
extensionless URL (`/l/font?kit=...`), and the loader then crashes on
the missing file extension -- vercel/next.js#99114. That made the CI
baseline build fail at random.

`rust/ci/font-mock.cjs` fixes it. next/font reads
`NEXT_FONT_GOOGLE_MOCKED_RESPONSES` as a module path and requires it;
the module maps a Google Fonts CSS URL to the CSS text. The mock
returns the captured CSS with every font URL rewritten to a local
path, and the loader reads the file from disk because the URL starts
with `/`.

The output is byte-identical to a live Google build: **2313 of 2315
files match**, the two exceptions being the manifests under the random
build id. The emitted font name is `xxhash64(content)`, so it does
not depend on the checkout path -- the same names appear on Windows
and on the Linux runner.

Regenerate it with:

```bash
node scripts/capture-font-mock.mjs
```

The capture patches next/font in `node_modules` for one build and
restores it, so it has to clear `.next` first -- a webpack cache
skips the font loader and the capture comes out empty. A CI step
fails when the mock no longer covers the vendored fonts, so a font
change cannot silently leave the baseline stale.

Two traps: `npm` is a shell script on Windows, so `execFileSync`
cannot spawn it -- the script invokes `node node_modules/next/dist/bin/
next build --webpack` directly. And `NEXT_FONT_GOOGLE_MOCKED_RESPONSES`
needs a **native** path (`F:/...`); the MSYS path (`/f/...`) is not
resolvable by `require`.

## Local builds

```bash
# The Pages build, locally (needs rustup + node).
./rust/build-pages.sh

# The Windows/MSYS build (MSVC target, rust-lld linker).
cd rust && cargo build --release --target x86_64-pc-windows-msvc

# Verify against the Next.js baseline.
npm run build
python rust/scripts/parity.py out out-rs
```

## Local toolchain notes

- `rust/.cargo/config.toml` sets `rust-lld.exe` as the linker for the
  MSVC target, so the generator builds on a machine without a full
  Visual Studio install.
- The Tailwind CLI is invoked from the `rust/` directory: Tailwind
  resolves the `content` globs relative to the working directory.
